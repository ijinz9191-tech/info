# 모든 언어에 공통인 시스템 개발 기초

확인일: 2026-09-30. 특정 프레임워크 API를 외우기 전에 아래의 계약을 설계하면 언어를 바꾸어도 오류를 줄일 수 있다.

## 동시성

- **경합:** 둘 이상의 실행 흐름이 같은 가변 상태를 다룰 때 읽기/쓰기 순서를 정의한다. 불변 값·메시지 전달·락·원자 연산 가운데 하나를 선택한다.
- **교착:** 여러 락을 함께 잡는다면 순서를 고정하고, 락 안에서 외부 I/O를 피한다. 취소·시간 제한을 정한다.
- **백프레셔:** 생산 속도가 소비 속도보다 빠르면 큐가 무한히 자란다. 큐 크기, 거부/대기 정책, 지표를 정한다.
- **비동기와 병렬:** 대기를 겹치는 것과 여러 CPU에서 계산을 수행하는 것은 다르다. 작업 종류에 맞는 실행기를 선택한다.

## 네트워크/API

요청은 지연·중복·유실·부분 성공을 겪을 수 있다. 타임아웃, 재시도 예산, 멱등 키, 오류 코드, 취소 전파를 설계한다. 재시도 가능한 작업인지 모르면 자동 재시도를 넣지 않는다. 상태 코드 하나가 실제 업무 완료를 증명하지 않는다. HTTP 의미는 [IETF RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html)을 기준으로 확인한다.

## 데이터베이스

| 문제 | 확인할 것 |
|---|---|
| 느린 조회 | 실제 실행 계획, 인덱스 선택, 반환 행 수, 정렬, 통계 |
| 중복/누락 | 고유 제약, 트랜잭션 범위, 재시도, 커밋 시점 |
| 동시 수정 | 격리 수준, 잠금, 낙관적 버전, 데드락 재시도 |
| 배포 실패 | 확장→전환→정리 단계의 스키마 호환성 |
| 연결 고갈 | 풀 크기, 대기 시간, 누수, 서버 연결 한도 |

SQL의 `NULL`은 일반 값과 동일하게 비교되지 않는다. 복합 인덱스의 열 순서와 실행 계획은 실제 DB 엔진에서 확인한다. [PostgreSQL 공식 문서](https://www.postgresql.org/docs/current/)를 참고한다.

## 테스트 전략

1. **단위:** 계산·검증·상태 전이의 빠른 경로를 검사한다.
2. **통합:** DB, 메시지, 파일, HTTP 경계에서 실제 직렬화·트랜잭션·실패를 검사한다.
3. **계약:** 생산자와 소비자가 같은 필드·오류·버전 의미를 공유하는지 검사한다.
4. **속성/차등:** 알고리즘 불변식이나 느린 정답 구현과 비교한다.
5. **장애 주입:** 시간 초과, 중복, 순서 변경, 부분 실패, 재시작을 재현한다.

테스트 통과는 테스트한 입력·환경에 대한 근거다. 실행하지 않은 플랫폼이나 외부 서비스의 안전성까지 확대하지 않는다.

## 보안 기본 경계

- 외부 입력은 길이·형식·허용값·권한을 각각 확인한다. 클라이언트의 타입 선언을 신뢰 경계로 쓰지 않는다.
- SQL은 매개변수화하고, 명령 실행은 가능하면 셸을 거치지 않는다. 출력 위치에 맞게 인코딩한다.
- 비밀값은 코드·로그·예제·오류 응답에 남기지 않는다. 최소 권한과 회전 경로를 설계한다.
- 의존성은 버전을 고정하고 업데이트 때 변경 기록, 테스트, 취약점 공지를 확인한다.

## 성능 측정

목표 지표를 먼저 정한다: 처리량, 평균/꼬리 지연, 오류율, 자원 사용량. 같은 입력과 환경에서 기준값을 측정한 뒤 한 변수씩 바꾼다. 마이크로벤치마크 개선이 실제 서비스 개선으로 이어지는지 프로파일·트레이스로 확인한다.

## 빌드 재현성

언어/컴파일러/SDK 버전, 잠금 파일, OS/아키텍처, 빌드 플래그, 환경 변수, 외부 서비스 버전을 기록한다. 로컬에서만 성공하는 경우에는 캐시·암묵 의존성·시간대·파일 경로 대소문자 차이를 확인한다.

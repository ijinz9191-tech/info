# 데이터베이스·데이터 처리·분산 시스템

확인일: 2026-09-30. 이 문서는 특정 제품 설정값보다 장애를 줄이는 설계 불변식을 기록한다. 제품별 보장과 SQL 문법은 버전별 공식 문서를 확인한다.

## 관계형 데이터와 트랜잭션

1. **모델:** 행의 고유 식별자, 외래키, `NOT NULL`, 유일 제약을 DB에도 둔다. 애플리케이션 검사만으로 동시 요청 간 경합을 막을 수 없다.
2. **쿼리:** 선택도 높은 조건·조인 키·정렬을 고려해 인덱스를 설계한다. 인덱스는 읽기를 돕지만 쓰기 비용과 저장 공간이 든다. 실제 통계와 `EXPLAIN`/실행 계획을 확인한다.
3. **트랜잭션:** 여러 쓰기가 하나의 불변식을 바꾸면 같은 트랜잭션으로 묶는다. 격리 수준에 따라 동시 트랜잭션에서 관측되는 현상이 다르다. 잠금 순서를 일정하게 하고 deadlock은 재시도 가능한 실패로 취급한다.
4. **마이그레이션:** 큰 테이블의 스키마 변경은 잠금·재작성·이전/새 버전 동시 실행 가능성을 검토한다. 백업만큼 복구 연습이 중요하다.
5. **연결 풀:** 요청 수 × 워커 수 × 풀 크기가 DB 연결 상한을 넘지 않는지 계산한다. 느린 쿼리, 풀 대기, DB CPU를 함께 본다.

오류 분류: `중복 키`는 비즈니스 충돌일 수 있고, `직렬화 실패·deadlock`은 재시도 조건일 수 있다. 같은 예외라도 무한 재시도하면 장애가 커진다. [PostgreSQL 문서](https://www.postgresql.org/docs/current/).

## 배치·스트림·분석

| 질문 | 결정·검증 |
|---|---|
| 입력이 늦거나 중복되는가? | 이벤트 시간과 처리 시간을 구분하고, 중복 제거 키와 허용 지연을 정한다. |
| 실패 후 다시 실행 가능한가? | 작업의 입력 범위, 체크포인트, 출력 커밋 경계를 기록한다. |
| 스키마가 바뀌는가? | 읽는 쪽과 쓰는 쪽의 호환성, 필수/선택 필드, 백필 순서를 검증한다. |
| 비용이 커지는가? | shuffle, 파티션 수, 데이터 skew, 파일 크기, 상태 저장량을 측정한다. |
| 결과가 정확한가? | 원본·중간·출력 건수, 합계, 샘플 키를 대조한다. |

[Spark](https://spark.apache.org/docs/latest/), [Flink](https://nightlies.apache.org/flink/flink-docs-stable/), [Airflow](https://airflow.apache.org/docs/)는 역할이 다르다. 엔진을 바꾸기 전에 요구가 배치 계산, 상태 기반 스트림 처리, 작업 오케스트레이션 중 무엇인지 결정한다.

## 메시징과 분산 실패

- **부분 실패:** 요청자가 응답을 못 받았어도 수신자가 작업을 끝냈을 수 있다. 타임아웃을 실패 확정으로 해석하지 않는다.
- **멱등성:** 쓰기 요청·이벤트에 안정적인 ID를 붙이고 처리 결과를 저장해 중복 시 같은 효과를 낸다. 보관 기간이 지나면 보장도 달라진다.
- **순서:** 전역 순서가 필요한지, 한 키 안에서만 필요한지 명시한다. 파티션 변경·재시도·병렬 소비가 순서를 바꿀 수 있다.
- **outbox:** DB 변경과 발행 의도를 같은 트랜잭션에 기록하고 별도 발행자가 전달한다. 중복 발행 가능성을 전제로 소비자도 멱등하게 만든다.
- **재시도:** 최대 횟수, 지수 지연, jitter, 최종 격리 위치를 둔다. 영구적 검증 오류와 일시적 네트워크 오류를 나눈다.
- **용량:** 생산 속도, 소비 속도, backlog 증가율, 복구에 필요한 시간을 함께 계산한다.

[Kafka 설계 문서](https://kafka.apache.org/design/), [CloudEvents 명세](https://github.com/cloudevents/spec/blob/main/cloudevents/spec.md), [Google SRE](https://sre.google/sre-book/)를 근거로 제품별 전달·내구성 계약을 확인한다.

## 장애 시 관측 순서

1. 사용자 영향과 최초 발생 시각을 확정한다.
2. 최근 배포·스키마·트래픽 변화와 대조한다.
3. 요청 지연을 앱, 네트워크, 풀 대기, DB 쿼리, 메시지 backlog로 나눈다.
4. 오류율뿐 아니라 재시도량·중복량·처리 지연·데이터 불일치를 본다.
5. 격리·롤백·트래픽 완화 뒤 데이터 정합성 복구 범위를 계산한다.

자세한 대응 기록 틀은 [장애 대응](incidents.md)에 있다.
